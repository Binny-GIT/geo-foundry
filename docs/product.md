# Geo Foundry 产品说明

- **状态**：现行产品方向
- **日期**：2026-08-27
- **适用范围**：内容运营控制台及其支撑的采集、编辑、审核、发布与更新流程

本文件是产品方向的唯一权威来源。上游《多站点 AI GEO 内容发布平台 PRD》是需求输入，不是实现合同；两者冲突时以本文件为准。`.omo/plans/geo-foundry-development-plan.md` 是 2026-08-18 的历史实施计划，仅作存档，不再约束新工作。

## 1. 产品定位

Geo Foundry 是 Xllent AI、Dianordic、NKMed 等少数几个自有品牌共用的**内容运营后台**。

各种来源的文章统一进入这里，由运营人员完成筛选、编辑、来源核对、品牌改写、审核、排期和发布，用于品牌的电子化推广。

核心业务链：

```text
稿源进入 → 筛选 → 编辑 → 来源核对 → 品牌版本 → 审核 → 排期 → 发布 → 更新
```

产品价值不在于「让 AI 写更多文章」，而在于：

1. 所有稿源集中到一个入口，不再散落在各个渠道。
2. 运营人员能快速判断哪些内容值得投入。
3. 一份内容可以针对不同品牌形成真正不同的版本，而不是复制粘贴。
4. AI 提高效率，但事实、表达和发布由人把关。
5. 每次发布都有来源、有审核记录、有版本、可回滚。

## 2. 非目标

以下能力不在当前产品范围内，除非后续有明确业务需求：

- 通用型大型 CMS 与页面搭建器
- 会员、评论、广告、电商
- 营销自动化平台
- 完整的 SEO 排名分析平台
- 实时协作编辑
- 面向外部客户的多租户 SaaS
- 用户访问请求中调用 LLM

生产环境的网站访问只读取已发布产物，不进入内容生产系统。

## 3. 用户与职责

| 角色 | 主要工作 |
| --- | --- |
| 编辑 | 处理稿源、撰写和改写内容、关联来源、提交审核 |
| 审核 | 检查事实与来源、批准或退回、写明退回原因 |
| 发布 | 安排发布时间、执行发布、处理发布失败与回滚 |
| 品牌负责人 | 维护品牌定位、语气、禁止表达和内容角度 |
| 管理员 | 管理站点、域名、用户、权限与系统状态 |
| 服务身份 | 采集器与 AI 服务通过接口写入，不使用人工界面 |

一个人可以同时具备多个角色。权限仍由服务端强制，界面隐藏不作为安全边界。

## 4. 对原始 PRD 的评审

### 4.1 保留

| PRD 内容 | 保留理由 |
| --- | --- |
| 内容与品牌版本分离（Content / Edition） | 一个主题服务多个品牌时，这个划分是正确的 |
| 禁止把同一篇文章直接复制到多个域名 | 直接对应多品牌推广的真实风险 |
| URL 作为一等实体，更新文章不改 URL | 避免推广链接失效 |
| 结构化正文而非纯 HTML | 支持预览、编译和后续复用 |
| 编译产出 SEO 与结构化数据 | 各站点不必重复实现 |
| 不可变发布、原子切换、可回滚 | 发布安全的基础 |
| 控制面与服务面隔离 | 后台故障时已发布网站仍可访问 |
| 质量检查分确定性规则、语义检查和 LLM 评估三层 | 避免完全依赖模型判断 |

### 4.2 重构

| PRD 内容 | 问题 | 调整方向 |
| --- | --- | --- |
| 以技术实体组织后台 | 运营人员被迫理解数据库结构 | 界面按任务组织，技术资源收进系统管理 |
| 单一固定状态机覆盖全部流程 | 无法表达筛选、待补来源、待排期等真实状态 | 拆成编辑状态、发布状态、质量状态三个维度 |
| 引用与实体以原始 JSON 维护 | 运营人员无法使用 | 改为来源面板与结构化表单 |
| Site 即品牌 | 缺少品牌定位与写作约束 | 在站点上增加品牌档案字段 |

### 4.3 推翻

| PRD 假设 | 推翻理由 |
| --- | --- |
| 产品定位为「内容基础设施平台」 | 实际是少数自有品牌的内部运营后台，不是对外平台 |
| 稿源接入、来源管理属于第二阶段 | 这是业务起点，必须进入首期 |
| 把 12 类底层资源作为运营主入口 | 与日常工作流不匹配 |
| 双站点 Demo 作为产品定义 | 那只是验收用的测试站点 |
| 需要通用页面搭建器式的灵活度 | 当前只有新闻/资讯类内容 |

### 4.4 延后

Content Planner、知识图谱、跨域语义查重的完整形态、多语言版本、AI 引用追踪、静态导出、社交与 Newsletter 分发，都等核心流程跑顺后再评估。

## 5. 业务流程

### 5.1 稿源进入

支持四种入口，统一归一为稿源条目：

| 入口 | 说明 |
| --- | --- |
| 手工录入 | 运营人员直接创建 |
| URL 导入 | 粘贴链接，由后台抓取正文 |
| Webhook / API | AI 服务、合作方或内部系统推送 |
| RSS | 定时轮询订阅源 |

每条稿源保存：来源渠道、原始标题与摘要、原始链接、抓取时间、正文快照、内容哈希、语言、重复标记。

原始响应与较大正文快照保存到对象存储，结构化元数据保存到数据库。

### 5.2 筛选

稿源箱中的可用动作：

```text
采用（选择目标品牌并创建文章）
忽略
标记重复 / 合并到已有内容
分配编辑
```

重复判断先用规范化链接、标题和内容哈希；语义查重后续再加强。

### 5.3 编辑与来源核对

稿件工作台需要同时提供：

- 正文编辑与页面预览
- 来源列表和原文对照
- 基础质量检查结果
- 负责人与截止时间
- 版本历史

关键约束：**结论性内容必须能追溯到具体来源**。缺少来源的稿件不应进入审核。

### 5.4 品牌版本

同一主题面向不同品牌时，各自是独立的文章，拥有各自的 URL、审核和发布记录，但共享稿源。

品牌档案约束写作方向：

```text
目标读者
专业领域
语气
禁止表达
内容角度
CTA
```

系统需要能对比两个品牌版本，避免出现实质重复的内容。

### 5.5 审核

审核意见必须绑定具体版本。批准后再修改内容，会产生新版本并使原批准失效。

退回修改必须填写原因，并写入审计记录。

### 5.6 排期与发布

发布计划包含：目标站点、计划时间、时区、状态。

到点后由后台任务执行编译、校验、上传和切换；发布是异步的，界面不得在请求返回时就宣称已发布。

发布失败必须可见、可重试，并保留失败原因。

### 5.7 更新

后期阶段引入：定期导入关键页面指标，识别流量下滑、内容过期或来源失效的文章，生成「建议更新」任务。

更新不直接改写已发布内容，而是创建新版本，重新走审核与发布。

## 6. 状态模型

不再用一个枚举覆盖全部流程。

**编辑状态**

```text
待筛选 → 编辑中 → 待审核 → 需修改 → 已完成
```

**发布状态**

```text
未计划 → 已排期 → 发布中 → 已发布 → 已撤回
```

**质量状态**

```text
未检查 / 有风险 / 已阻止 / 已通过
```

底层内容版本状态机（`draft`、`generating`、`review`、`approved`、`compiled`、`published`、`archived`）继续作为服务端的安全约束，但不再直接作为界面的组织方式。

## 7. 界面信息架构

一级导航：

```text
今日工作
稿源箱
内容库
发布计划
品牌与站点
系统管理
```

**今日工作**按角色显示待办：分配给我的稿件、待我审核、审核退回、今日待发布、失败任务。不做所有角色统一的指标看板。

**稿源箱**采用列表加右侧预览的分栏结构，支持按渠道、品牌、重复度和状态筛选。

**内容库**以文章为单位，可按品牌、状态、负责人、日期和来源筛选。

**稿件工作台**采用三栏：

```text
左：来源与历史    中：正文 / 预览    右：质量、审核与发布
```

**发布计划**先提供按日或按周的列表视图，不引入拖拽日历组件。

**系统管理**收纳用户、租户、URL 记录、质量评估、发布版本、回滚意图和操作记录。这些是管理员和排障入口，不属于日常运营导航。

## 8. 界面原则

1. 运营界面使用业务语言，不暴露 ID、哈希、operation、release 等技术词。
2. 状态用文字表达，颜色只作辅助。
3. 受限与零值必须区分清楚，不得用 `0` 冒充无权限。
4. 列表是可操作队列，不是数据库表格。
5. 技术审计信息默认折叠。
6. 中文优先，英文可切换。
7. 桌面与移动端均不允许横向溢出。

## 9. 范围划分

**第一阶段**

稿源箱与四种入口、筛选与去重、稿件工作台、来源关联、审核与退回原因、负责人与截止时间、品牌档案、发布计划与定时发布、不可变发布与回滚。

**第二阶段**

品牌版本对比、AI 辅助生成与改写、批量筛选、语义查重、内部链接建议、审核意见沉淀。

**第三阶段**

页面表现数据导入、更新建议、内容合并与下线建议、更多分发渠道。

## 10. 验收场景

第一阶段完成时，应能完整走通：

1. 通过四种入口各导入一条稿源。
2. 在稿源箱中忽略一条、合并一条、采用两条。
3. 采用的稿源分别为两个品牌创建文章。
4. 编辑正文并关联来源。
5. 提交审核，审核退回并填写原因。
6. 修改后重新提交并批准。
7. 设置计划发布时间。
8. 到点后自动发布，站点可访问且 URL 稳定。
9. 修改文章后重新发布，URL 不变。
10. 回滚到上一版本。
11. 全流程在权限范围内执行，跨租户不可见。
