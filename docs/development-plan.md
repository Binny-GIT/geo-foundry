# Geo Foundry 开发计划

- **状态**：现行计划
- **日期**：2026-08-27

本文件取代 `.omo/plans/geo-foundry-development-plan.md`。那份 40 任务计划面向 2026-08-18 的旧产品方向，仅保留为历史存档。

产品目标见[产品说明](product.md)，技术边界见[架构说明](architecture.md)。

## 阶段划分

计划分七个阶段。每个阶段都必须交付可用能力，不做纯重构阶段。

---

## 阶段一：文档与界面所有权

**目标**：确立唯一的产品方向和唯一的界面实现。

工作项：

- 建立本套文档（已完成）。
- 明确控制台是唯一产品界面，Payload 原生后台仅作应急入口。
- 停止向 Payload 自定义产品视图添加新功能。
- 统一 Zod、React、Next.js 版本。

验收：

- 新文档与代码现状一致，不存在把旧 PRD 或双站点 Demo 描述为现行合同的表述。
- 依赖版本在整个工作区一致，构建与测试通过。

---

## 阶段二：精简脚手架

**目标**：移除与产品规模不匹配的平台化机制，降低后续每次改动的成本。

工作项：

- 删除 `apps/content-service`，其接口并入控制面 Route Handler。
- 将 `packages/*` 全部改为内部包，移除 API Extractor 配置、`api:check`、`packages:validate`、`packages:pack-smoke` 及相关消费者脚本。
- 移除逐任务证据与回执体系，改用常规 CI 测试产物。
- 将 `.test/` 下的一次性循环脚本与需求矩阵合并为少量 Playwright 用例。
- 故障测试只保留发布、回滚与幂等相关部分。
- 处理遗留路由：`/console/*`、`/admin/work`、`/admin/history`、`/admin/system`、`/admin/tenant` 要么实现，要么删除。

验收：

- 构建、类型检查、单元测试与浏览器用例全部通过。
- 部署流程不依赖被删除的脚本。
- 仓库中不再存在从未部署的应用。

---

## 阶段三：稿源箱

**目标**：让内容真正有统一入口，这是产品的业务起点。

工作项：

- 新增 `connectors`、`intake-items`、`source-snapshots`。
- 实现四种入口：手工录入、URL 导入、Webhook/API、RSS 轮询。
- URL 与 RSS 抓取、正文提取作为 `content-intake` 后台任务执行；手工与 webhook 保持同一 IntakeItem 结构。
- 原始响应与正文快照以不可覆盖对象写入对象存储，元数据与 SHA-256 写入数据库。
- 基于规范化链接、标题和内容哈希做重复检查。
- 控制台新增稿源箱页面：列表加右侧预览、按渠道与状态筛选。
- 支持采用、忽略、标记重复、合并、分配品牌与编辑。

验收：

- 四种入口各导入一条稿源，均归一为同一结构。
- 重复稿源被正确标记，不产生重复文章。
- 采用稿源可创建文章并保留来源关联。
- 抓取失败可见、可重试，且不会丢失稿源条目；Worker 拒绝 loopback、私网、metadata、非默认端口和重定向逃逸。

---

## 阶段四：稿件工作台

**目标**：让编辑与审核在一个界面内完成，不再依赖底层资源页。

工作项：

- 控制台内保留唯一一套内容编辑实现，移除重复编辑器。
- 工作台改为三栏：左侧来源与历史，中间正文与预览，右侧质量、审核与发布。
- 新增 `article-sources`，在正文中关联来源。
- 新增 `review-comments`，退回修改必须填写原因。
- 内容版本增加负责人、优先级、截止时间。
- 引用与实体改为结构化表单，移除面向运营人员的原始 JSON 编辑。
- 今日工作页按角色显示待办。

验收：

- 编辑可关联来源并提交审核。
- 审核可批准或退回，意见绑定具体版本。
- 批准后修改内容会产生新版本并使原批准失效。
- 编辑冲突有明确提示，不会静默覆盖他人修改。

---

## 阶段五：排期与发布

**目标**：补齐定时发布，这是当前缺失的关键能力。

工作项：

- 在 compose 中用同一镜像新增 Worker 服务，命令切换为 worker 角色，并通过 owner-only 凭据文件引用获得 CMS、Redis、对象存储与 AI Provider 配置。
- 新增 `publication-plans`：目标站点、计划 UTC instant、创建时的 IANA 时区快照、状态和关联 operation。
- Worker 每秒轮询到期计划；操作账本 reconciliation 仅在启动时及低频兜底恢复时执行。CMS 以 PostgreSQL revision 条件更新原子 claim，Redis delayed job 不作为计划事实源。
- 到点后复用既有 publisher 授权、编译、校验、上传与指针切换链路；发布计划页提供按日或按周列表。
- 发布失败可见、可重试，保留失败原因；取消与 Worker 恢复不得产生重复发布。
- 站点管理增加品牌档案字段。

验收：

- 计划只接受明确的 UTC instant，并保存与站点一致的 IANA 时区快照；不接收会产生 DST 歧义的本地墙上时间。
- 设置计划时间后，由一个 Worker 原子领取、创建或重放既有 publisher 授权的发布 operation；页面可访问。
- 修改文章后重新发布，URL 保持不变。
- 可回滚到上一版本，且不重新编译。
- 发布任务或到期计划重复投递不会产生重复发布。
- Worker 停止后重启，未完成 operation 与 running plan 可恢复并收敛为终态。

---

## 阶段六：品牌版本与 AI 辅助

**目标**：让一份内容高效服务多个品牌。

工作项：

- 支持从一篇文章为其他品牌创建版本。
- 品牌档案约束写作方向。
- 提供两个品牌版本的差异对比。
- AI 生成与改写作为后台辅助任务，结果进入草稿，不自动发布。
- 语义查重用于提示跨品牌实质重复。

验收：

- 同一主题的多个品牌版本拥有各自 URL、审核和发布记录。
- 内容实质重复时有明确提示。
- AI 结果必须经人工确认才能进入审核。

---

## 阶段七：表现与更新建议

**目标**：让发布之后仍有闭环，但不建设分析平台。

工作项：

- 新增 `performance-snapshots`，由受保护的 JSON / CSV 导入接口写入少量关键指标；相同导入哈希必须幂等。
- 识别流量下滑、内容过期或来源失效的文章。
- 生成可解释的「建议更新」任务并进入今日工作。

验收：

- 同一导入不会重复写入，更新建议只针对已发布版本并给出可解释的触发数据。
- 更新创建新草稿并重新走来源、质量、审核与发布，不直接修改已发布内容。

---

## 测试范围

只针对真实业务风险，不追求覆盖率数字：

1. 四种稿源统一归一。
2. 重复检查。
3. 品牌与角色权限，跨租户不可见。
4. 内容版本不可变。
5. 审核绑定版本。
6. 编辑冲突。
7. 任务幂等与重试。
8. 定时发布与到期计划的 revision claim。
9. 发布产物不可覆盖。
10. 回滚到旧版本。
11. Worker 同镜像 Compose smoke：消费 Outbox、处理 `content-intake` 并领取 due publication plan。
12. 一条完整浏览器路径：导入 → 采用 → 编辑 → 审核 → 排期 → 发布 → 回滚。

不再要求每个任务产出专用证据文件，测试报告与日志走常规 CI 产物。
