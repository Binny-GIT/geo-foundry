# ADR 007：内容运营领域模型

- **状态**：已采纳
- **日期**：2026-08-27

## 背景

系统原本从「已经存在一条内容」开始建模，把稿源接入、来源管理和内容规划放到第二阶段。

但实际业务的起点是：各种 AI、采集系统和渠道进来的文章需要统一收口、筛选和加工。缺少这一层，运营人员无法回答内容从哪里来、是否重复、是否可信、该给谁做。

同时，界面按数据库集合组织，把租户、URL 记录、质量评估、发布版本、操作记录等技术实体暴露为一级导航，与日常工作流不匹配。

## 决策

### 补齐运营领域

新增以下实体，全部以现有数据层实现，不引入新的基础设施：

```text
connectors            采集渠道：手工 / URL / Webhook / RSS
intake-items          稿源条目：状态、重复标记、建议品牌、负责人
source-snapshots      原始响应与正文快照、内容哈希
article-sources       文章版本与稿源的关联
review-comments       审核意见
publication-plans     计划发布时间、时区、状态
performance-snapshots 页面表现（后期阶段）
```

现有实体的最小扩展：内容版本增加负责人、优先级、截止时间；站点增加品牌档案字段（目标读者、专业领域、语气、禁止表达、内容角度、CTA）。

### 刻意不引入的抽象

- **不新增独立 Brand 实体。** Xllent AI、Dianordic、NKMed 各自就是一个站点加品牌档案。再加一层 Tenant → Brand → Site 只会增加映射成本。
- **不新增独立任务实体。** 负责人与截止时间直接挂在稿源条目和内容版本上，等「一稿多任务」真实出现时再拆。
- **不建设完整 Fact / Claim 知识图谱。** 先用文章版本与稿源快照的关联表满足溯源需求。
- **不新增任务账本。** 复用现有异步操作记录。

### 状态模型拆分

不再用单一枚举覆盖全流程，改为三个维度：编辑状态、发布状态、质量状态。底层内容版本状态机继续作为服务端安全约束，但不再直接决定界面结构。

### 界面按任务组织

一级导航为：今日工作、稿源箱、内容库、发布计划、品牌与站点、系统管理。

租户、用户、URL 记录、质量评估、发布版本、回滚意图、操作记录移入系统管理，作为管理员与排障入口。

## 后果

- 稿源接入成为第一阶段能力，产品有了真正的起点。
- 运营人员面对业务对象，不再直接操作数据库集合。
- 领域实体数量受控，避免过早抽象带来的维护负担。
- 品牌与站点合一，代价是将来一个品牌需要多个站点时要做一次拆分；在当前规模下这个取舍是划算的。
- 数据溯源能力先满足「结论可追溯到来源」，暂不追求段落级事实图谱。
