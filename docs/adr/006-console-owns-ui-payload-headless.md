# ADR 006：控制台负责界面，Payload 作为后端

- **状态**：已采纳
- **日期**：2026-08-27

## 背景

管理端一度同时存在两套产品界面：自研的 Next 控制台，以及大量定制过的 Payload 原生后台视图（仪表板、导航、工作队列、版本工作区、操作详情、发布历史、系统诊断、租户工作区）。

两套实现意味着每个功能要做两遍，视觉与行为持续不一致，运营人员也需要在两种交互模型之间切换。

同时，产品评审确认真正的问题是**产品模型缺失**（稿源、任务、品牌档案、排期、表现），而不是后端框架选错。Payload 提供的登录、API Key、角色权限、租户范围、媒体上传、草稿与版本、数据库迁移，对单团队维护的内部产品是净收益；自行重建这些会显著增加成本却不解决产品问题。

## 决策

`/admin` 下的 Next 控制台是**唯一的产品界面**。

Payload 保留为后端：数据模型、认证与会话、RBAC、租户范围、媒体与对象存储、草稿与版本、数据库迁移。

Payload 原生后台仅保留在 `/admin/_emergency`，限超级管理员使用，作为控制台不可用时的应急入口。它不接收新的产品功能，产品导航中也没有入口。

浏览器读写统一走同源接口，服务端读取以当前会话身份执行且不绕过访问控制。工作流关键写入必须经过领域服务与受保护命令端点，不允许前端用通用 CRUD 直接修改状态字段。

## 后果

- 产品界面只有一套实现，视觉与交互一致。
- Payload 定制的产品视图在控制台达到等价能力后删除。
- 不再为「Payload 后台也要能用」付出额外适配成本。
- 更换后端底座的成本被限定在数据访问层，而不是散落在整个界面。
- 应急入口仍然存在，排障时不必依赖数据库直连。

## 实现依据

- `apps/cms/src/app/(console)/`
- `apps/cms/src/console/`
- `apps/cms/src/payload.config.ts`（`routes.admin` 指向 `/admin/_emergency`）
